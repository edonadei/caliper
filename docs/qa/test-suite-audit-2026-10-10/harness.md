## Evidence and implementation model

The full implementations inspected are `caliper/harness/base.py`, `claude_code.py`, `codex.py`, `hermes.py`, `pi.py`, `mcp.py`, `prompt_failure.py`, `refusal.py`, `user_layer.py`, `windows_job.py` in the same directory, plus `caliper/environment.py`, `workdir.py`, `backends.py`, `harness/__init__.py`, and `commands/update_cli.py`. Relevant `McpServer` validation in `schema/spec.py`, judge failure handling in `judge/eval_judge.py`, run environment/metadata assembly in `runner.py`, customization warnings and ablation labels in `compare.py`, customization defaults in `schema/results.py`, and report header rendering in `reporter.py` were read. Shared fakes in `tests/conftest.py` and CI at `.github/workflows/lint.yml` were read in full. Contributor guidance, ADR 0005, 0020, the connectors ADR 0026, and ADR 0035 were read. Historical commit messages/diffs were inspected for #237, #271, #218 and the original update CLI addition.

`CliHarness.run` owns readiness, home seeding, preparation, user staging, skill installation, command/environment construction, attempt-local MCP preflight, process execution, timeout recovery, stream reading, refusal interpretation, salvage and `AttemptResult` assembly. It normalizes a model into a copy of the input context. Adapters supply real protocol differences. Claude passes its prompt on argv and materializes a short-lived JSON MCP file. Codex passes its prompt through file-backed stdin and rewrites TOML. Hermes runs oneshot and export in a shell, preserving the oneshot exit code, and can recover persisted sessions after timeout. Pi uses positional prompts with stdin closed and interprets errors from zero-exit JSON streams.

The conformance suite tests common behavior across four adapters. It deliberately overlaps some policy tests. A shared test calling `_seed_home` does not prove that each adapter declares the right files. Likewise a direct `_read` refusal test does not prove `run` raises the right exception with the right login command. Tests at both levels are justified where those are different contracts.

`patch_cli_calls` mocks both capability `subprocess.run` and agent `Popen`, adapting communicate to a CompletedProcess-shaped fake. Assertions about external argv, stdin, cwd, env and config payloads are observable process-boundary contracts. They are unlike an assertion that a private helper was called. This fake does not validate real Windows process creation, subprocess text encoding, pipe drains, shell syntax, process tree termination or actual CLI compatibility; the real process and paid smoke tests fill those gaps.

## Strengthen or repair

### Host isolation and update side effect

`tests/test_update_cli.py:90`, `test_update_cli_refuses_codex_app_bundle`, constructs and patches a fake `CODEX_APP_CLI`, then invokes `update-cli codex --yes`. It does not clear `CODEX_CLI_PATH`, mock `shutil.which`, or mock `subprocess.run`. `caliper/harness/base.py:892` resolves an existing explicit path before install candidates. `caliper/commands/update_cli.py:197` suppresses bundle advice whenever the override variable is nonempty. The parent baseline had a real override pointing into the ChatGPT app, so the fake bundle was ignored and the test ran real `npm install -g @openai/codex`. Baseline output reported `changed 2 packages in 9s`; the test then failed because CLI invocation exited 0 rather than 1. This is executed evidence supplied by the parent, corroborated by inspected code.

Repair by controlling all resolver inputs and installing a fail-closed subprocess fake before invoking the app. For the bundle branch that fake should raise if any external command is attempted. A hermetic fixture should clear `CODEX_CLI_PATH`, `HERMES_CLI_PATH` and `PI_CLI_PATH` unless a test explicitly supplies them, and keep real CLI/config locations out of fake-agent tests. Do not merely clear the variable at invocation: a future broken bundle guard must still be unable to perform a host update. Keep this test's refusal code and message assertions.

The same `CODEX_CLI_PATH` leak caused baseline failures in `tests/test_codex_harness.py:29` (`test_codex_installs_the_skill_and_leaves_the_prompt_alone`), :265 (`test_codex_prefers_app_bundled_cli`), :344 (`test_codex_fails_clearly_when_cli_requires_newer_version`), and `tests/test_update_cli.py:12` (`test_update_cli_check_prints_versions`) and :55 (`test_update_cli_updates_with_npm_when_confirmed`). Those other tests have process fakes, so their host override shows up as a mismatch/failure or an unintended fake branch rather than a real install. `_run_codex_mcp` already clears `CODEX_CLI_PATH`; direct early Codex tests do not consistently do so. Most early Pi tests similarly never clear `PI_CLI_PATH`; Hermes `_install` does clear its override. `test_update_cli_all_updates_every_npm_cli_around_a_self_updating_one` correctly clears all three and fakes `subprocess.run`.

A related production behavior worth separate analysis is a stale nonempty `CODEX_CLI_PATH`: discovery falls back to a bundle, but `_app_bundle_env_var` still suppresses bundle refusal because it tests env presence rather than whether that override was used. This slice has no direct stale-override update regression. Do not change production during the audit.

### Explicit gaps in this slice

- CLI update failure return codes, missing npm, denied confirmation and invalid target are not tested in the assigned update CLI module. Add only behavior that is worth maintaining; do not build a test per helper.
- Adapter protocol mocks prove that commands/configs are emitted, not that a renamed upstream flag is still accepted. Keep paid smoke evals and record live CLI versions when running them.
- Literal backend seed requirements are not all independently pinned. Pi models.json and Hermes exclusion are covered; generic declaration-derived seeding cannot establish the full inventory.
- Real Pi capability refusal is absent. The static declaration and generic backend guard are separate checks with a wiring gap.
- User customization union across attempts with differing inventories and a mixture of known/unknown inventories is not exercised by the identical `gmail` scripted results in `test_user_customizations.py`. `runner._recorded_customizations` unions only known lists. Its edge-case meaning should be decided and tested through `run`, rather than through a self-referential helper expected value.
- User-skill name validation, unreadable/malformed installed plugin registry/manifest, missing plugin installations, explicit plugin manifest namespaces/extra skill paths, and symlink cycles in user skills have implementation branches not covered by this assigned module. Other slice owners may find overlap; this is not a claim of repository-wide absence.
- Config allowlists mostly test removed behavior. Literal custom provider endpoints and credential-store options surviving isolation deserve observation because deleting all config can satisfy removal-only checks. The shared verbatim seed test cannot replace Codex's rewritten TOML path.
- Real Windows readiness/Node/preflight/workdir tests are gated, but adapter-specific argv/config tests are excluded from Windows CI. Quoting, UTF-8 and file permissions tested only on POSIX do not prove native Windows behavior.
- Remote MCP connections are not preflighted here. The localhost header smoke tests actual auth transmission, while DeepWiki smoke tests public remote transport. Neither should be represented as comprehensive remote auth/OAuth coverage.
- Empty results in `test_refusal.py`, no MCP declarations, missing init inventories and unknown customization records are intentional protocol values. They are not deletion candidates just because they assert `None`, `{}` or `[]`.
